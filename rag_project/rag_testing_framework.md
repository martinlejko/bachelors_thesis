# RAG System Testing Framework

## Introduction

This document outlines the comprehensive testing framework implemented for the RAG (Retrieval-Augmented Generation) system developed as part of this bachelor's thesis. The testing framework is designed to systematically evaluate the performance of different RAG pipeline iterations, ensuring a rigorous and reproducible assessment methodology.

## Testing Architecture

The testing framework leverages two primary technologies:

1. **Pytest**: A robust Python testing framework that provides the structural foundation for organizing and executing tests.
2. **DeepEval**: A specialized library for evaluating LLM-based systems, offering metrics specifically designed for RAG system assessment.

This combination allows for both automated testing workflows and detailed quality assessments of RAG outputs.

## Test Data Structure

### JSON Test Cases

Test cases are defined in a structured JSON format, allowing for clear organization and easy maintenance. Each test case captures the essential components needed for RAG evaluation:

```python
{
    "market_trends_2023": {
        "question": "What were the key market trends in 2023?",
        "expected_output": "The stock market saw a strong rebound driven by technology stocks and easing inflation.",
        "context": ["Investors regained confidence as inflation cooled and central banks slowed interest rate hikes."]
    },
    "inflation_decline_causes": {
        "question": "What were the main reasons for the decline in inflation?",
        "expected_output": "Supply chain improvements and higher interest rates helped reduce inflation.",
        "context": ["The Federal Reserve's monetary policy and stabilization of global supply chains played key roles."]
    }
}
```

Key components of each test case:
- **question**: The user query input to the RAG system
- **expected_output**: The gold-standard answer that serves as the benchmark for evaluation
- **context**: Reference information that contains the facts needed to answer the question correctly

When executed, the test framework extends these test cases with:
- **actual_output**: The answer generated by the RAG system
- **retrieval_context**: The document chunks retrieved by the RAG system's retriever component

### Test Dataset Creation

The `EvaluationDatasetFactory` class provides a mechanism to transform these JSON test case definitions into DeepEval's `LLMTestCase` objects:

```python
dataset = EvaluationDatasetFactory.create_from_dict_with_invocation(test_data, qa_pipeline)
```

This factory method:
1. Iterates through each test case in the JSON configuration
2. Executes the RAG pipeline to obtain the actual system output and retrieved context
3. Constructs a proper `LLMTestCase` with all required parameters
4. Combines these into an `EvaluationDataset` that can be processed by DeepEval

## Evaluation Metrics

The testing framework employs four key metrics from DeepEval's GEval class, each addressing a specific aspect of RAG system quality:

1. **Answer Correctness** (threshold 0.7):
   - Evaluates if the system's answer is factually correct based on the expected output
   - Uses the input query, actual output, expected output, and context as parameters

2. **Answer Relevancy** (threshold 0.7):
   - Assesses if the response directly addresses the question asked
   - Uses the input query and actual output as parameters

3. **Conciseness** (threshold 0.8):
   - Determines if the response is appropriately concise (within three sentences) while remaining clear
   - Uses only the actual output as a parameter

4. **Context Relevancy** (threshold 0.7):
   - Evaluates if the retrieved contexts contain information relevant to answering the query
   - Uses the input query and retrieval context as parameters

These metrics are instantiated in the `get_default_metrics()` function and are applied consistently across all iterations of the RAG pipeline.

## Cross-Iteration Testing Architecture

A key strength of the testing framework is its ability to systematically evaluate and compare different iterations of the RAG pipeline:

1. **Iteration Structure**:
   - Each iteration is organized in a dedicated directory (`src/iterations/iter_X/`)
   - Iterations represent systematic variations in the RAG pipeline (e.g., chunking methods, embedding models, retrieval parameters)

2. **Dynamic Pipeline Loading**:
   - The framework uses dynamic imports to load the appropriate pipeline module from each iteration
   - This is managed through Pytest fixtures that parametrize the iteration name:

```python
@pytest.fixture(params=get_iteration_modules())
def iteration_name(request):
    """Parametrized fixture that yields each iteration name."""
    return request.param

@pytest.fixture
def qa_pipeline(iteration_name):
    """Initialize RAG pipeline for the specified iteration."""
    module_path = f"src.iterations.{iteration_name}.pipeline"
    pipeline_module = importlib.import_module(module_path)
    pipeline = pipeline_module.create_pipeline(
        use_web_urls=False,
        use_pdf=True,
        use_confluence=False,
        force_refresh=True,
    )
    return pipeline.query
```

3. **Consistent Test Execution**:
   - The same test cases are applied to each iteration
   - This ensures fair comparison across different pipeline configurations

## Testing Workflow

The complete testing workflow follows these steps:

1. **Setup**:
   - Import required modules and test cases
   - Initialize the evaluation metrics

2. **Pipeline Instantiation**:
   - For each iteration, dynamically load the corresponding RAG pipeline

3. **Test Case Processing**:
   - For each test case:
     - Submit the question to the RAG pipeline
     - Capture the generated answer and retrieved documents

4. **Evaluation**:
   - Create an evaluation dataset with the processed test cases
   - Apply the defined metrics using DeepEval's evaluate function
   - Compare outputs against thresholds to determine pass/fail status

5. **Results Storage**:
   - Save detailed test results to JSON files:
     ```python
     json_file = save_test_results(result, iteration_name)
     ```
   - Generate HTML reports for visualization:
     ```python
     html_file = save_report(json_file)
     ```

6. **Analysis**:
   - Compare results across iterations to identify improvements or regressions
   - HTML reports provide detailed view of performance on each metric

## Running the Tests

The testing framework can be executed using the standard Pytest command-line interface:

```bash
poe test-iterations
```

This command:
1. Discovers and executes all test functions in the testing module
2. For each iteration, runs the complete test suite
3. Generates comprehensive results in both JSON and HTML formats
4. Saves results to the `test_results/` directory

## Results Visualization

The framework produces two types of result files:

1. **JSON Results** (`results_{iteration_name}_{timestamp}.json`):
   - Contains detailed test data including:
     - Test case information (question, expected output)
     - System output (actual answer, retrieved context)
     - Performance metrics (scores, thresholds, pass/fail status)
     - Overall success indicators

2. **HTML Reports** (`results_{iteration_name}_{timestamp}.html`):
   - Provides an interactive, visual representation of test results
   - Includes:
     - Overall success rate with progress bar
     - Summary statistics (total tests, passed, failed)
     - Detailed results for each test case
     - Metric scores with pass/fail indicators
     - Side-by-side comparison of expected and actual outputs

These reports facilitate both detailed analysis of specific test cases and high-level comparison across iterations.

## Conclusion

The implemented testing framework provides a robust methodology for evaluating and comparing different RAG pipeline configurations. By using standardized test cases, consistent metrics, and automated execution, the framework ensures:

1. **Objectivity**: Consistent evaluation criteria across all pipeline variants
2. **Reproducibility**: Tests can be re-run with the same conditions to verify improvements
3. **Comparability**: Results can be directly compared across iterations to measure impact of changes
4. **Detailed Analysis**: Granular metrics provide insights into specific aspects of performance

This framework has been instrumental in guiding the iterative development process, allowing for data-driven decisions when refining the RAG system architecture.
